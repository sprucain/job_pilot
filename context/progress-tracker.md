- **04 Database Schema** — Confirmed via `run-raw-sql` before writing any DDL that InsForge's Postgres is Supabase-shaped: `auth.users(id uuid, email, ...)` plus `auth.uid()`/`auth.email()`/`auth.role()`/`auth.jwt()` helper functions, and `anon`/`authenticated` roles already have default-privilege grants (`arwd`) on any new `public` table — so table-level GRANTs are automatic and RLS policies are the only thing actually restricting per-row access. Used `auth.uid()` in every policy accordingly, matching the InsForge SDK's own DB-query rule ("always scope to `user_id`") at the database layer too, not just in app code.
- **04 Database Schema** — All four tables (`profiles`, `agent_runs`, `jobs`, `agent_logs`) created exactly per architecture.md's column list, with RLS enabled and four policies each (select/insert/update/delete, all `USING`/`WITH CHECK (user_id = auth.uid())`, `profiles` using `id = auth.uid())` since its PK *is* the user id). Added a few things architecture.md doesn't spell out but that were clearly implied: `profiles.id` has an explicit `REFERENCES auth.users(id) ON DELETE CASCADE`; foreign keys `agent_runs.user_id`/`jobs.user_id`/`agent_logs.user_id` all `REFERENCES profiles(id) ON DELETE CASCADE`; `jobs.run_id` and `agent_logs.job_id` are nullable with `ON DELETE SET NULL` (matches "null if from URL input" in architecture.md); `jobs.source` and `agent_logs.level` got `CHECK` constraints enforcing their documented enum values; indexes added on every foreign key plus `jobs.match_score`/`jobs.found_at` since Feature 11 (Filter + Sort + Pagination) will sort/filter on exactly those; a `profiles_set_updated_at` trigger auto-maintains `updated_at` on every update (`created_at`/`updated_at` both `DEFAULT now()`).
- **04 Database Schema** — `resumes` storage bucket created with `isPublic: false`. Architecture.md's "own files only" half of the access rule is **not** enforced by Postgres RLS — `storage.objects` has no `owner`/`user_id` column comparable to `auth.uid()` (only `uploaded_by text`, `bucket`, `key`), so per-user path isolation for `resumes/{user_id}/resume.pdf` relies on the InsForge SDK/API layer checking the authenticated caller against the path, not on a custom RLS policy written here. Flagging so Feature 06 (Profile Save Logic, which does the actual upload) doesn't assume a database-level guarantee that isn't there.
- **04 Database Schema — `/review` findings resolved (2026-09-08)** — `/review` found one Important and three Minor issues. Fixed: (1) **Important** — `agent_runs.status` had no `CHECK` constraint even though `jobs.source`/`agent_logs.level` (the same category of documented enum column in architecture.md) both did; added `agent_runs_status_check CHECK (status IN ('running','completed','failed'))`, confirmed via `pg_constraint`. (2) **Minor** — dropped the `DELETE` policy on all four tables (`profiles_delete_own`, `agent_runs_delete_own`, `jobs_delete_own`, `agent_logs_delete_own`); no feature in build-plan.md performs a delete anywhere (job-dismiss and profile-deletion are both explicitly out of scope per project-overview.md), so RLS now denies DELETE entirely by default rather than granting unrequested scope — confirmed via `pg_policies`, 12 policies remain (select/insert/update × 4 tables). A future feature that genuinely needs deletion should add its own policy deliberately rather than relying on this leftover one. (3) **Minor** — struck build-plan.md's Feature 04 "tailored fields" bullet for the `jobs` table; it contradicted both architecture.md's actual schema and project-overview.md's explicit "Resume tailoring per job" / "Score recalculation after tailoring" out-of-scope entries — nothing was ever built for it, this just removes the stale instruction. (4) **Minor** — corrected build-plan.md's Feature 16 text, which said to sort `agent_runs` by "created_at descending" — that column doesn't exist on `agent_runs` (only `started_at`/`completed_at`, per architecture.md); now reads "started_at (agent_runs) / found_at (jobs) descending" to match the real schema.
- **04 Database Schema — unresolved verification gap (documented, not fixed)** — `/review` also flagged that RLS's actual cross-user isolation was verified only structurally (policies exist, reference `auth.uid()` correctly), not empirically — `run-raw-sql` always executes as `postgres` (`rolbypassrls = true`) and the MCP tool explicitly rejects `SET ROLE`/`set_config()` ("Changing SQL execution role... is not allowed"), so this sandbox has no way to simulate a second authenticated user's session. This is an environment limitation, not something fixable in this session — carry it forward: confirm real cross-user isolation once two real user sessions exist (or via an authenticated PostgREST/SDK call with two different real JWTs), rather than assuming the structural check is sufficient.
